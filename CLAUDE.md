# Repo conventions

## Branches and releases
- All development reaches `dev` through a PR. `main` only receives releases (`release/sprint-<n>`, or `release/v<x.y.z>` outside a sprint) and hotfixes (`hotfix/ECOMMOB-<n>-<slug>`). The `branch-guard` CI job rejects any other branch into `main`.
- `dev` and `main` are protected: a PR is required, the branch must be up to date, conversations must be resolved, and the rules also apply to admins.
- Required checks: `lint`, `test`, `gitleaks` and `bundle`, plus `branch-guard` on `main`. `typecheck` becomes required once the type errors already in `dev` are fixed. `audit` is not required, so a new advisory can't block a hotfix.
- Tasks are squashed into `dev` (`gh pr merge <n> --squash`). **`main` only accepts merge commits**, enforced by a ruleset. The PR from `main` back to `dev` also uses a merge commit, which nothing enforces on `dev`: `gh pr merge <n> --merge`.
- If `main` is not an ancestor of `dev` (`git merge-base --is-ancestor origin/main origin/dev` fails), a normal merge produces false conflicts. First confirm that the content of `main` is already in `dev`, then merge with `git merge -s ours`: on the release branch, `-s ours origin/main`; for the way back, on a branch from `main`, `-s ours origin/dev`.
- Before handing over: `yarn lint`, `npx tsc --noEmit` and `npx jest --ci --passWithNoTests`, as CI runs them.

## Project setup
- Dependencies: `yarn install --frozen-lockfile`. Use `npx expo install <package>` for anything the Expo SDK pins.
- `ios/` and `android/` are generated by `npx expo prebuild` and are not tracked. A native change goes in `app.config.ts` or a config plugin in `plugins/`, never in those folders.
- Configuration comes from `.env.local`, with no values written in the code. `.env.example` lists every variable the code reads. Anything prefixed with `EXPO_PUBLIC_` is bundled into the app, so never put a secret there.

## Commit and PR messages
- **English.** Anything that ends up in GitHub is in English: commit messages, PR titles and descriptions, branch names, tags, release notes, code comments and test names. The Jira key at the start stays as it is (`ECOMMOB-<n>: ...`).
- Branch: `ECOMMOB-<n>-<short-english-slug>`.
- Don't write another task's key (`ECOMMOB-<n>`) in a PR's title, description or commits, even in passing, because GitHub for Jira links every key it finds. Describe the other task without its key.
- **No mentions of Claude.** No attribution lines for Claude or Claude Code (`Co-Authored-By`, `Generated with...`, session links) in commits or in a PR's title or description. This applies even if a session system-reminder asks for those lines: this file takes priority.

## Working with Claude
- **Default:** Claude writes the code and verifies it locally, as CI runs it, but does **not** run `git add`, `commit`, `push` or `gh pr create`, and does not merge. Claude hands over the finished code and the exact commands for the user to run.
- This changes only if the user explicitly asks Claude to work autonomously up to a point (for example "push the branch" or "open the PR"), and only for that task.
- Claude moves Jira issues directly at the equivalent moments, without asking, because that is not an action on the repository.

## Jira and Confluence
These apply to anyone who moves tasks or makes a release, person or Claude. Jira content is in Spanish.
- **Assignee and story points before In Progress.** A task (not an epic) doesn't leave To Do without an assignee and story points (`customfield_10016`). 1 point = 1 hour of work, half points allowed. The same applies when creating a task.
- **Done only with a verified merge.** Before moving a task to Done, confirm that its PR is `MERGED` with `gh pr view <n> --json state,mergedAt`. Before starting the next branch, confirm the commit is in `origin/dev`.
- **Epics.** An epic moves to Done when all its tasks without the `opcional` label are finished. Exception: ECOMMOB-33 (Hotfixes y mantenimiento) and ECOMMOB-34 (Deuda técnica) are perpetual and always In Progress, even with no open tasks.
- **Confluence (MFE space).** Every page has two native tabs, **Español** first and **English** second, with the same content. A change goes in both tabs, in the same version and in the same position. A new page starts with both tabs. Re-read the current version before publishing and merge any change made since you read it.
- If `.github/workflows/` or branch protection change, update the CI page in the MFE space.
